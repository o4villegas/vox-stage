# VoxStage — state of the application, 2026-09-08

Status: **assessment only.** No application code was written or changed (rule 1). Every
statement below is either measured in this session (command + output in the appendix, or a
screenshot named in the text) or labelled **[judgment]**. Screenshots live in the session
scratchpad, not the repo. Requested by Lando: "a comprehensive, empirically-based assessment
of the current state of this application… I have reason to believe we need extensive
front-end work."

## 1. The short version

- **What exists is small, healthy, and live.** One Cloudflare Worker at
  `https://vox-stage.therancch.com` serves a phone-first web app with exactly three screens:
  *enter your email → enter the six-digit code → a signed-in placeholder home*. Every
  automated gate passes (style check, type check, 27 tests, build, deploy check), the live
  bundle is byte-identical to a local build of `main`, and the page loads in ~130 ms with
  zero layout shift. The whole front end is about 350 lines of React and 470 lines of CSS.
- **Lando's instinct is right, with one correction.** Extensive front-end work *is* needed —
  but not because what exists is poor. It is because **nearly all of the product's screens
  do not exist yet** (profile capture, upload and processing status, the synced player, live
  scoring, results, history, settings), and **the foundation those screens need has not been
  laid**: no navigation/URL routing, no design-token scale or component library, no data
  layer, no error boundary, no offline/installable-app support, no visual or end-to-end
  tests. Three of the four remaining product milestones (M3 profile capture, M4 player,
  M5 scoring) are front-end-dominant.
- **Seventeen concrete defects were measured in what exists** (§4.3: 2 high, 8 medium,
  7 low). None blocks a tester today. The two high ones: **"Sign out" can silently fail
  and still show the sign-in screen** (the server session survives; a reload is signed in
  again), and **keyboard focus is thrown away after every failed submit** (and after a
  successful sign-in). The rest: the signed-in home does not fit common phones, one colour
  fails the contrast minimum, no navigation state, "declared iPhone floor vs. CSS used"
  mismatches, installable-app and offline gaps, a dead screen on a stalled connection, and
  hygiene items. Every claim was re-run by an independent verification agent (24 of 25
  confirmed, one set of numbers corrected) and a second, independent design audit scored
  the app 49/100 and reached the same recommendation (§10).
- **Recommendation (§8): approve a short front-end foundation milestone before M2**, folding
  the twelve defect fixes into it, so M2–M5 screens are built on a system rather than
  retrofitted at M6. Options A/B/C with what would flip the recommendation are in §8.

### 4.2 Strengths (measured — keep these)

- **Craft is real, not template.** A deliberate direction ("stage light": aubergine field,
  amber spotlight, cream type, Fraunces display + Inter body), an entrance animation for the
  spotlight and card, film grain, a shake on a wrong code, and a full
  `prefers-reduced-motion` fallback. It does not look like a default component kit
  (screenshots `signin-390x844`, `code-error-390`).
- **Form details are right for phones:** `inputMode="email"/"numeric"`,
  `autoComplete="email"/"one-time-code"` (iOS Mail code autofill), non-digits stripped on
  paste, focus moved into the code box on arrival (measured: active element = `code`),
  disabled submit until six digits, 30-second resend cooldown, rate-limit and wrong-code
  messages come from the server in plain English, `role="status"` + `aria-live` on the
  message line, labelled inputs, ≥ 53 px tall targets.
- **Numbers:** Lighthouse accessibility 100; LCP 131 ms; CLS 0; 62 KB gzip total JS; no
  overflow at six widths; both fonts load.
- **Engineering hygiene:** shared API types between app and Worker, strict TypeScript,
  Biome, isolated-D1 Worker tests, CI on every PR, Workers Builds previews per branch.

## 8. Options for the front-end work (decision for Lando)

**Option A — Front-end foundation milestone before M2 (recommended).** One approved
milestone, one draft PR: fix F1–F17; add routing + layout shell; a token scale and the
first component primitives (built from the existing "stage light" system, not replaced);
a data layer; error boundary + offline/online; self-hosted fonts; installable PWA (icons +
service worker); coverage provider + threshold, Playwright E2E on the preview URL and
screenshot regression at 320/390/768/1440; security headers + `robots.txt`;
`AUTH_DEV_ECHO=0` when the sending domain lands; and a designed **microphone-permission
pattern** (explain → ask → a "you said no" state with the Settings route back) before M3,
because iOS grants exactly one system prompt. Estimate **[judgment]**: 2–3 sessions. The
independent UX audit reached the same recommendation on its own (its "Option B", §10.2).
*Why:* three of the four remaining product milestones are front-end-heavy, and the
mandate's quality bar comes from system + motion + polish, which is far cheaper to lay
once than to retrofit at M6. *What would flip it:* if proving the GPU pipeline (S2 →
M2) is the make-or-break question for the whole product, do Option B first — the two
do not conflict technically, only in sequencing.

**Option B — Proceed straight to M2 as planned; fold the foundation into M6 hardening.**
Fastest route to a real upload→ready loop. *Cost:* M2's status UI, M3's capture UI, M4's
player and M5's scoring get built without a system, then reworked at M6 (the pattern that
produced F2/F4 already, at 350 lines). *Exception that makes B right:* Lando wants beta
demand signal as early as possible and is fine with a rougher look until M6.

**Option C — Fix the seventeen defects now in one small PR; defer the foundation.** About
one session; the app is measurably better for the same three screens; nothing structural
changes. (The UX audit also priced a fourth path — adopt an off-the-shelf component library
and build a full system on it — and argued against it here: generic libraries pull toward
a template look and add weight on older iPhones; it becomes right only if a second
front-end developer is joining soon.) *Exception that makes C right:* Lando wants zero structural front-end investment
until S2's cold-start number is in hand, but does not want to leave known defects live.

**Recommendation: A, with C's fixes as its first commit.** Nothing starts until Lando says
so (rule 1).
